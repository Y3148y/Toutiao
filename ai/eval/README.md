# RAG 检索质量评估

回答一个此前无法回答的问题：**这套 RAG 的召回率到底是多少。**

## 快速开始

```bash
# 1. 导出语料（改了database.sql 就重跑）
python -m ai.eval.export_corpus

# 2. 当前配置的基线指标
python -m ai.eval.runner --baseline --k 1,3,5,8

# 3. 参数网格扫描，输出权衡表
python -m ai.eval.runner --sweep --top-k 5
```

## 两个必须说清楚的限制

### 1. 阈值在单路模式下无法标定

参数扫描的原始结果：

| MIN_FUSION | Recall@5 | 拒答率 | 误召回 | 正例作答 |
|---|---|---|---|---|
| 0.004 | 93.9% | 0% | 100% | 100% |
| 0.008 | 93.9% | 0% | 100% | 100% |
| **0.012** | 93.9% | 100% | 0% | **0%** |
| 0.020（线上值） | 93.9% | 100% | 0% | 0% |
| 0.040 | 93.9% | 100% | 0% | 0% |

0.008 → 0.012 之间是**断崖**：从「全放行」直接跳到「全拒答」，中间没有可调空间。

原因：单路最高分恒为 `1/(60+1) × 0.5 ≈ 0.0082`，所有 55 条用例挤在同一分数上，阈值区分不出强相关和弱相关。

**结论：`MIN_FUSION_SCORE=0.02` 这个值我当初是按 RRF 公式手算的，
它从未被真实数据验证过。在向量路可用之前它无法被有效标定。**

### 2. 假向量不能用来论证向量路的收益

`--vector` 用的是 SHA-512 派生的确定性哈希向量，它**没有任何语义**。
实测 top20 候选的余弦分数跨度只有 0.022~0.072 —— 所有文档分数几乎挤在一起，
排名近似随机。

它只能回答一个问题：**融合机制在某一路退化时会不会崩**（答案是会，MRR 腰斩）。
它**不能**回答「向量检索把召回率从多少提升到多少」—— 那必须用真实 embedding 测，
需要 `DASHSCOPE_API_KEY`：

```bash
python -m ai.eval.runner --baseline --vector-real
```

本文件里所有数字都标注了向量路状态，不要混用。

### gold 是怎么来的 —— 重要限制

`gold` 是**按新闻标题反推**的，不是人工标注。所以它衡量的是
「检索能否找回标题里包含那些词的文档」，而不是「这篇新闻是否真的回答了这个问题」。

后者需要人工判断。50 条够看出数量级和趋势，**不足以做精细调优**。
正式标定必须人工过一遍评估集。

## 指标定义

| 指标 | 公式 | 用途 |
|---|---|---|
| Recall@K | 前K条中命中任一 gold 的比例 | 衡量「该找到的找到了」 |
| 完整召回率@K | 前K条中找齐**全部** gold 的比例 | 多 gold 用例的严格衡量 |
| MRR@K | `mean(1/首个命中排名)` | 排序质量，命中靠后等于答不出 |
| nDCG@K | `DCG/IDCG`，位置加权 | 对所有命中位次计分 |
| 拒答准确率 | 负例中被正确拒答的比例 | 幻觉来源之一 |
| **误召回率** | 负例中被放行的比例 | **幻觉的直接指标** |

只用新闻 ID 集合运算，不需要人工标注相关性 —— 这是能把质量门禁放进 CI 的前提。

Recall 与误召回必须一起看：只优化 Recall 很容易靠放宽阈值把幻觉率同步放大。

## CI 门禁

`tests/test_rag_quality.py` 在每次 PR 上跑，**纯本地 BM25，不调任何 API，约 3 秒**。

当前阈值是**故意设得很宽**（Recall@5 ≥ 0.75、误召回率 ≤ 0.35）：
宽是为了先跑起来、不阻塞日常开发，它只挡灾难性退化。

### 门禁的实测边界（重要，不要高估它）

我实测了两次故意破坏，门禁**都没拦住**：

| 注入的缺陷 | 实际指标变化 | 门禁结果 |
|---|---|---|
| 关闭中文二元组过滤（只留单字匹配） | Recall@5 93.9%（**不变**） | 9 passed ✅未拦住 |
| 去掉标题双次加权 | Recall@5 93.9%、MRR@5 90.5%（**均不变**） | 未拦住 |

原因：评估集里 16 条同义改写类用例都能靠二元组命中，单字噪声没有推高误召回；
而标题权重的差异在这个 403 条语料上没体现到 top5 排序。

**结论：这个门禁只挡「检索彻底失效」这一档。**
上面两个缺陷在真实线上会产生明显更差的召回，但门禁是绿的。
要真正拦住，需要更大更难的评估集（含同义改写占比更高、干扰项更密），
或引入线上真实查询日志做回归基线。这条已记入下轮待办。

## 已知问题（本轮未修）

| 问题 | 实测数据 | 影响 |
|---|---|---|
| **embedding 缓存 N+1** | 每查询 **404 次 Redis 往返 / 1497ms** | 逐条 GET 拼向量，403 条已不可接受 |
| **向量检索纯 Python** | 403×1024 维遍历 **72.7ms/次** | 未用 numpy 矩阵乘 |
| **BM25 索引每次重建** | tokenize 403篇 **38.4ms** + 重建打分 **35.9ms** | 每查询固定 56ms |
| **无检索链路 trace** | 只有 request_id 级HTTP 日志 | 无法复盘「为什么排出这个结果」 |
| **评估集未人工校验** | gold 按标题反推 | 衡量的是词面命中而非语义正确性 |

性能三项合起来约 1.6 秒/查询（向量可用时）。这是下一轮的事，
本轮刻意不做 —— 没有基线数字时优化等于盲改。
