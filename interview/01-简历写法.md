# 01 · 简历写法

> 目标：让面试官看完这段，**想追问**，而不是一眼看完就翻页。

---

## 📄 通用版（直接可用）

> 复制到简历时把「项目名称」换成你自己的说法，数字不要改 —— 都是实测值。

```
今日头条新闻资讯平台（个人项目 / 独立开发）
技术栈：Python · FastAPI · SQLAlchemy 2.0 · MySQL · Redis · Pytest · Docker

面向新闻消费场景的资讯平台后端，支持信息流、分类、搜索、热度榜与相关推荐，
并在此基础上实现基于新闻语料的语义检索与可溯源问答。

• 独立完成 27 个 API 的后端服务，覆盖注册登录、新闻浏览、搜索、收藏、
  历史与相关推荐，基于异步 SQLAlchemy + Redis 令牌桶限流落地，并配套
  Docker Compose 编排与 GitHub Actions 多版本 CI。

• 针对「用户只记得内容、不记得标题」的痛点设计语义问答能力：自建
  BM25 + 向量双路混合检索链路，以 RRF（k=60）融合两路排序，在 55 条
  标注评测集上 Recall@5 达 93.9%、MRR@5 达 90.5%。

• 引入三级置信判控（向量余弦 → BM25 分数 → RRF 兜底），在证据不足时
  主动拒答而非让模型编造，将负例误召回率降至 16.7%，拒答准确率 83.3%，
  且正例召回无损失（Recall@5 保持 93.9%）。

• 构建离线索引流水线：语料校验、内容指纹、增量更新与断点续跑，语料
  变更时仅对增量文档调用向量化 API（403 篇中仅新增 1 篇时，API 调用
  从 403 次降至 1 次，构建耗时 2793ms → 428ms）。

• 定位并优化两处检索瓶颈：BM25 索引随语料指纹进程内缓存，查询 74.3ms
  → 2.1ms；语料向量由逐条 Redis 取值（404 次往返）改为批量读取
  （1 次往返），向量扫描 72.7ms → 0.26ms。

• 修复 15 组共 33 篇完全重复新闻在检索侧挤占结果位次的问题，改为按
  内容哈希在召回后去重、保留融合分最高的一条；并将索引 content_hash
  由一对一改为一对多映射，避免入库阶段静默覆盖。
```

## 🎯 为什么是这 6 条

排列顺序是刻意的，对应面试官的注意力曲线：**先确认你是个能交付的工程师，再确认你在做有深度的事**。

| # | 这条在证明什么 | 面试官大概率追问 |
|---|---|---|
| 1 | **能独立交付**：业务完整、有部署有 CI | 「限流怎么做的？Redis 挂了怎么办？」 |
| 2 | **懂检索本质**：知道为什么要混合，不是跟风加向量 | 「为什么不用纯向量？」 |
| 3 | **有产品判断**：宁可拒答也不编 | 「你怎么知道能降低误召回？」 |
| 4 | **工程化能力**：懂离线/增量/成本 | 「增量更新怎么做？断了怎么办？」 |
| 5 | **性能意识**：会定位瓶颈而非瞎优化 | 「你怎么知道瓶颈在哪？」 |
| 6 | **数据严谨性**：会去重、会修根因 | 「为什么按内容哈希去重？」 |

**为什么第 6 条不可省**：只写性能优化的简历，面试官读完的印象是「这是个调参项目」。有一条真实的业务数据修复，才能证明你是在**做产品**而不是做 benchmark。

**为什么性能拆成两条（4、5）**：一条讲离线构建、一条讲在线查询，分别对应两个不同的追问场景，合并会让追问点模糊。

## 🔍 简历中每个 Bullet 的面试官关注点

> 这一节是本文档最重要的部分。简历上的每一行，在面试官眼里都是一个**待展开的承诺**。
> 下面逐条给出他们会问什么、以及你应该准备到什么深度。

### Bullet 1 · 27 个 API / 限流 / CI

- **追问方向**：令牌桶为什么用 Lua？Redis 挂了会怎样？CI 跑什么？
- **你应该能答出**：
  - Lua 保证「读计数 + 扣减 + 写回」的原子性，否则并发下会超发
  - Redis 故障时 **fail-open** 放行 —— 限流是保护措施，为它牺牲可用性是本末倒置
  - CI 跑 Python 3.10/3.11/3.12 全量测试，验证兼容性
- **⚠️ 雷区**：别说「Redis 挂了降级成 5 QPS」—— 那是凭空造需求。诚实答「直接放行，记 warning 日志」。

### Bullet 2 · 双路混合检索 / Recall@5 93.9%

- **追问方向**：为什么 BM25 和向量都要？RRF 是什么？评估集怎么标的？
- **你应该能答出**：
  - BM25 对**专名和数字**不可替代（`GDP`、`5.2%`）；向量擅长**跨表述**（「高铁延长运行时间」≈「动车组新增班次」，零字面重叠但 BM25 得分为 0）
  - 两路分数**量纲不同**（BM25 无上界、余弦 ∈ [-1,1]），不能直接相加，所以用 RRF 只看排名
  - 55 条用例按类别均衡分布（经济/科技/外交/社会/政策各 10 条 + 6 条负例）
- **⚠️ 雷区**：说「人工标注了 55 条评估集」。`gold` 是**按新闻标题反推**的，衡量的是「检索能否找回标题含那些词的文档」，不等于「这篇新闻是否真的回答了这个问题」。
- **⚠️ 雷区**：别说「向量检索比关键词准」。这是本项目最容易被问倒的认知错误 —— 真实的向量增益是 **0**（见 `04` 第 2 题），吹了会在追问里塌房。

### Bullet 3 · 三级置信判控 / 16.7%

- **追问方向**：三级是哪三级？为什么不能只看一个分数？怎么证明有效？
- **你应该能答出**：
  - **向量余弦（主）**：正例中位 0.80 / 负例中位 0.48，天然有区分度
  - **BM25 分数（降级）**：向量服务不可用时 RRF 会恒定，判据会失效，必须换有真实幅度的分数
  - **RRF（兜底）**：语义最弱，只在前两者都拿不到时用
  - **有效性证明**：召回率 93.9% / MRR 90.5% **前后完全不变**，只提升拒答能力 —— 这是「零代价优化」的强证据
- **⚠️ 雷区**：**不要主动说「原来是 100%」**。简历只写终态。面试真问到，见 `04` 第 4 题的答法。

### Bullet 4 · 离线索引 / 增量更新

- **追问方向**：怎么判断哪些文档变了？中断了怎么办？索引版本怎么管？
- **你应该能答出**：
  - 按**内容哈希**（title+description+content）比对，只对新增/变更的文档调 embedding
  - **三重版本校验**：语料指纹 + embedding 模型名 + 向量维度，任一不匹配就废弃索引重建
  - 写进度文件支持**断点续跑**，失败不用从头再来
- **⚠️ 雷区**：只说校验「模型名」是不够的 —— 同一模型不同版本维度可能变，必须同时校验维度。

### Bullet 5 · 性能优化

- **追问方向**：怎么定位瓶颈的？为什么缓存没有一致性问题？
- **你应该能答出**：
  - BM25 的开销在**构造索引**而非打分（tokenize 38.4ms + 建索引 35.9ms = 74.3ms），而语料不变时索引完全不变 → 按语料指纹缓存是安全的
  - 向量侧瓶颈是**逐条 Redis GET**（404 次往返 1497ms），改批量读取后降到 1 次
  - 关键是「**随语料缓存而非每次重算**」这个思路，不是「加了个缓存」
- **⚠️ 雷区**：性能数字必须带「实测」前提。面试官若问「什么机器、什么负载」，如实说是本地压测即可。

### Bullet 6 · 33 篇重复新闻

- **追问方向**：为什么会有重复？是入库的问题还是检索的问题？为什么不直接删库？
- **你应该能答出**：
  - 根因在**入库侧**：`content_hash` 原本是一对一唯一约束，后来的重复数据**静默覆盖**了先前记录
  - 修法：入库改**一对多映射**（33 篇都保留）+ 检索侧按哈希**召回后去重**（保留融合分最高的一条）
  - 为什么两侧都要改：只改检索侧，入库仍在丢数据；只改入库侧，用户仍会看到重复结果
- **⚠️ 雷区**：这题在考你是否**找到根因**而非打补丁。答案里一定要出现「根因在入库侧」这层。

## ✍️ 写法规则（血泪总结）

这三条是本文档最有价值的部分。它们和写代码的直觉相反 —— 但按代码直觉写简历，会在面试现场付出代价。

### 规则 1 · 不写中间态数值

| ❌ 不要这样写 | ✅ 这样写 |
|---|---|
| 负例误召回率从 100% 降到 16.7% | 负例误召回率 16.7% |
| 分词方案优化后 MRR 从 90.5% 降到 88.4%（已回退） | （不写） |

**原因**：`100% → 16.7%` 在简历上读起来像「代码写坏了」。而且简历是**结果展示**，不是实验日志 —— 中间态留给面试问答讲，反而是加分项。

### 规则 2 · 不主动暴露短板

项目确实有边界：403 篇语料规模小、只测了检索没测生成忠实度、没做大规模压测。**这些一条都不要写进简历。**

- ❌ 「支持小规模语料，大规模场景待验证」
- ❌ 「暂未实现向量数据库，403 篇用 NumPy 够用」

**原因**：主动暴露短板，面试官的记忆里就只剩短板了。**但被问到要如实回答** —— 那时你在展示判断力（见 `04` 压力题）。

### 规则 3 · 自我介绍不展开项目细节

自我介绍只讲：**个人信息 → 技能栈 → 实习/实践产出 → 项目一句话**。

❌ 「我这个项目用了 FastAPI，然后检索层是 BM25 加向量双路，RRF 融合，k 取 60，然后置信门控分三级……」

✅ 「我做了一个新闻资讯平台的后端，最近主要在它的语义问答能力上做检索优化 —— 具体细节您想从哪个部分听？」

**原因**：简历上有的东西面试官自己会看。你主动倒豆子，他会觉得你在背稿；你给出引导，他会觉得你有结构。

### 规则 4 · 每条 bullet 必带数字

「优化了检索性能」→「优化了检索性能（74.3ms → 2.1ms）」。

没有数字的 bullet 等于没写。面试官靠数字判断你的工作量和真实性。

## 🔄 常见问题自查

写完简历，对照检查：

- [ ] 有没有出现「从 X 降到 Y」的句式？
- [ ] 有没有主动写「暂未实现」「有待验证」？
- [ ] 每条 bullet 是否都有数字或可验证的事实？
- [ ] 有没有一条 bullet 是在讲**业务价值**而不全是技术指标？
- [ ] 技术栈是否和代码里**真实使用**的完全一致？
- [ ] 能不能预判每条 bullet 的第一个追问是什么？

最后一条最重要 —— **预测不到追问，说明你对那条 bullet 的理解还不够深。**
